## Сначала проверь freshness

До анализа напиши, что ты фактически видишь:

- revision/status документа V3.5;
- scene count;
- prompt count;
- work items;
- slow scenes;
- schema version `project-status.json`;
- текущий GitHub commit SHA, если доступен.

Если видишь не `17 scenes / 20 prompts / W5,W7,W8 / slow 2,6,14,15`, прямо укажи, что источник отличается от baseline, и не делай вид, что анализируешь актуальную версию.

## Твоя задача

Попытайся **сломать именно Phase 1 implementation plan**.

Ищи только реальные failure modes:

- потеря данных;
- появление второго master / split-brain;
- stale state, который выглядит свежим;
- ложный `health: ok`;
- перезапись хорошей GitHub-инструкции плохим/неполным Drive download;
- race condition между manual trigger и scheduled run;
- status JSON и файлы из разных snapshots;
- ослабление защиты slow-generation;
- duplicate render;
- schema v3, ломающая текущий `index.html`;
- malformed `scene-meta`, который слишком легко валит production pipeline;
- dependency metadata, превращающаяся во второй источник сюжета;
- неверный rollback;
- auto-repair инструкций, который может восстановить устаревшую Drive-версию;
- возможность внешнему ИИ принять generated state за editable source;
- приватные данные, случайно попадающие в публичный JSON/GitHub Pages.

## Не надо

Не предлагай:

- переносить canonical master с Google Drive;
- создавать второй master;
- менять scene IDs;
- переписывать все prompts;
- менять художественные решения;
- добавлять тяжёлый backend/DB без доказанной необходимости;
- редизайн сайта ради внешнего вида;
- оценку вида «9.8/10» без конкретных technical findings.

## Для каждого finding дай

1. **Severity:** CRITICAL / HIGH / MEDIUM / LOW
2. **Exact location:** файл + раздел/шаг
3. **Failure scenario:** конкретная последовательность событий, при которой проблема проявится
4. **Impact:** что реально ломается
5. **Minimal fix:** минимальное изменение, не перестраивающее всю систему
6. **Regression risk:** что может сломать твой fix
7. **Verdict:** BLOCKER BEFORE PHASE 1 / FIX BEFORE MERGE / ACCEPTABLE RISK

Не создавай finding, если не можешь описать конкретный failure scenario.

## Отдельно ответь на 12 вопросов

1. Может ли partial/HTML Drive download перезаписать рабочую GitHub-инструкцию?
2. Может ли workflow опубликовать `instruction_sync=ok`, когда committed files реально отличаются?
3. Может ли `scene-meta` стать скрытым вторым source of truth?
4. Правильно ли render state вычислять из существующего slow-list вместо пятого ручного поля?
5. Может ли schema v3 нарушить backward compatibility текущего сайта?
6. Есть ли race/stale-run риск у `cancel-in-progress: true` + schedule + push trigger?
7. Атомарен ли proposed commit с точки зрения master/instructions/status?
8. Что случится, если один из пяти Drive instruction IDs временно недоступен?
9. Достаточен ли rollback без отката Drive master?
10. Стоит ли optional malformed `scene-meta` валить весь health, или нужен иной уровень ошибки?
11. Безопасно ли требовать dependency target только среди active scenes, учитывая удаление закрытых сцен из active master?
12. Есть ли более простой способ получить те же guarantees с меньшим количеством state?

## Финал

В конце выдай только:

### BLOCKERS
Только реальные blockers. Если их нет — так и напиши.

### FIX BEFORE MERGE
Конкретные правки до реализации.

### ACCEPTABLE RISKS
Что можно осознанно оставить.

### GO / NO-GO
- `GO` — Phase 1 Step A можно реализовывать после перечисленных fixes.
- `NO-GO` — есть unresolved blocker; объясни какой именно.

Не хвали документ. Цель — найти, где он сломается.
