# Серёгиус: технический сбой не останавливает очередь

Статус: действует. Проверено: 30.10.2026.

Решение владельца 30.10.2026 (МСК), открытый ChatGPT Work: «при возникновении ошибки … были попытки запустить повторно … а если не выходит то следующую на очереди». Задача №1 — не оставлять подтверждённые свободные слоты без готовой разрешённой работы. Действует для открытого Work, часового задания `6acae6ab433481919e88665c520b8ef2` и существующего Relay handler через `ops/TOPVIEW-FREE-LAUNCH.md`.

## Область разрешения

Только выбранные видео текущей очереди Серёгиуса, доска My First Board `1a6244cf1ae747ef847d949a80d6133c`, сайт Unlimited, видимая цена 0. Это заменяет прежний общий запрет технических автоповторов и старые счётчики одноразового разрешения **только при подтверждённом техническом сбое по условиям ниже**. `max_new_submissions` остаётся историческим бюджетом первого запуска; новый бюджет хранится отдельно. Редакционные переделки удачно сгенерированного видео, owner hold, отменённые/заменённые/архивные пункты, пробы Стича, другие проекты и платные запуски этим решением не разрешены. Очередь, выбранная модель, полный промпт и настоящие зависимости/QC сохраняются.

## Проверка и ограниченные повторы

1. В каждом цикле сначала fresh main/решения владельца, очередь и полный скан всех досок/страниц. Сверить существующие task IDs и незавершённые claims **до выбора следующего пункта**, даже если readiness скрывает `submitted`. Активная `init/queued/running/processing` задача занимает слот: ожидание Topview само по себе не ошибка.
2. Различать подтверждённый `fail/failed` без пригодного результата; явный отказ интерфейса до создания задачи; и неизвестный исход. `claim/submitting/submission_unknown`, сетевой таймаут после возможного Create, `Task not found` или отсутствие в скане сами по себе не доказывают неотправку. Искать по task ID, полному нормализованному промпту, времени, точным входам и предыдущим receipts; найденный запуск принять, не дублировать. Пока исход неизвестен — сохранить историю и запретить повтор этого item/зависимых частей; независимая очередь продолжается при проверенной свободной ёмкости.
3. При подтверждённом техническом сбое найти и по возможности устранить причину. Входы проверить по SHA, фактическим миниатюрам, размеру, количеству и порядку `@ImageN/@VideoN`; отклонённый файл не должен смещать следующий в его слот. Использовать сохранённый корректный transport-файл из manifest; не перерисовывать входы и не менять творческий замысел ради повтора. Непригодный вход, модерационный отказ, недоступный бесплатный режим или неустранимая ошибка — конкретный blocker и переход к независимому готовому пункту, без повторения неизменённого заведомо плохого запроса.
4. Разрешены **не более двух дополнительных Create-попыток на item** по этой политике, общий счётчик `retry_attempts_used` для Work/часового задания/Relay. Между подтверждённым техническим отказом и следующим Create — около 60 секунд; свободный слот и полный preflight проверить заново. Успешная постановка в очередь прекращает повторы. Если ошибка повторилась и бюджет исчерпан, `blocked_retry_exhausted`, причина и следующий шаг; больше не повторять без нового решения владельца. Новый час/событие, смена чата, исправление входа или новый task ID бюджет не обнуляют.
5. До каждого повторного Create под собственным canon-lock и CAS сохранить прежний `task_id`, claim, исход и receipt в `submission_history`; создать `retry_control` с `policy_id: owner-20261030-technical-retry`, `retry_attempts_used`, `max_retry_attempts: 2`, `last_error`, `last_attempt_at`, `retry_not_before`, `attempts[]`. В одной атомарной записи увеличить счётчик, сохранить evidence подтверждённого отказа/исправления и новый уникальный claim; перенести старую terminal-задачу в историю, не стирая её provenance. После readback нажать Create один раз. Неизвестный исход расходует эту попытку и блокирует повтор до выяснения. Уже исчерпанный/неясный счётчик восстановить из истории, не назначать ноль по отсутствующему полю. Подтверждённый task ID/параметры/входы/стоимость → `submitted` и отдельная квитанция. Если безопасно подготовить повтор нельзя — сохранить blocker, не расходовать Create-попытку.
6. При временном сбое браузера **до Create** — до двух повторов доступа/чтения с паузой около минуты по `ops/TOPVIEW-EVENT-WAKE.md`; они не расходуют Create-бюджет. Общий недоступный браузер/неполный скан/полные слоты не обходить. Записать `blocked_browser` и точный следующий шаг; следующее настоящее пробуждение проверяет доступ заново без ожидания «Продолжай».
7. Исчерпанный бюджет, локальный blocker, ожидание результата или `retry_not_before` **не резервируют слот**. В том же цикле выбрать следующий независимый готовый item с минимальным живым priority. После каждого подтверждённого запуска пересчитать ёмкость и продолжить до заполнения слотов либо исчерпания готовой разрешённой работы. Не менять относительные приоритеты и не выдавать новый рендер за художественную приёмку. Сохранить checkpoint/register и снять свой замок; Relay дополнительно сохраняет квитанцию каждого event_id по своему протоколу.

Для S59-P2 и S62-P1 сейчас существуют подтверждённые активные исправленные задачи: их не перезапускать. Прежнее неизвестное отправление S62 остаётся в истории и само по себе не получает нового разрешения. Новый бюджет применим к будущему подтверждённому техническому отказу выбранной актуальной попытки, после сверки отсутствия активного дубля.
