# Серёгиус: Dot и Grok — согласованные исполнители

Статус: действует. Проверено: 18.11.2026.

Пробуждение, роли и предупреждения сайта — `ops/PRIMARY-BACKUP-WAKE.md`. Ниже — общий замок, claim v2, intent, verify-before-create и один Create. Обёртка — `ops/LAUNCHER-ENTRY.md`. Прежние роли и расписания — `archive/ops/wake-roles-until-2026-11-15.md`.

## Одна очередь, один отправитель

1. Fresh main, разрешения владельца, общий полный учёт всех досок, master/manifests/SHA/QC — по `ops/TOPVIEW-FREE-LAUNCH.md`. Сначала reconciliation всех `claimed/submitting/submission_unknown` и уже отправленных task IDs. Успех Topview не является одобрением.
2. Каждый реальный вызов генерирует отдельный UUID `execution_instance_id`; это **не** runtime run ID. Holder: `chatgpt:ordinary:<UUID>`, `chatgpt:work:<UUID>`, `grok:<UUID>` или `minimax:<UUID>`. Общее имя `chatgpt` не доказывает владение. Перед записью взять общий `ops/canon-lock.json` отдельным CAS-коммитом и прочитать обратно. Чужой непросроченный замок не перехватывать. Для launch-операции брать короткую разумную lease и продлевать только при настоящем выполненном шаге; не имитировать прогресс.
3. Перед каждой записью/claim/Create повторно читать реестр, `route_generation`, точный holder, `acquired_at`, срок lease и собственный item claim. Потеря роли или lease немедленно запрещает старому вызову писать/нажимать Create. Для интерактивного чата также проверять `foreground_owners.<surface>.session_id/epoch`.
4. После полного UI-preflight сохранить уникальный claim с execution UUID, route generation и исходным SHA. Непосредственно перед единственным Create отдельной атомарной записью перевести собственный `claimed` в `submitting` с `submission_intent_id` и временем. **Сначала CAS и readback, затем ровно один клик в том же непрерывном исполнении.** Повторный вызов, разрыв после intent, expired lease и новый чат не разрешают второй клик; такой исход сверяется. `scripts/launcher_coordination.py` проверяет роль/lease/claim и одноразовый переход; сам видео не запускает и git не публикует.
5. Подтверждённый task ID, полный текст/входы/параметры/Unlimited0 — receipt и `submitted`. Неизвестный исход — сохраняется, не обнуляется по TTL. Неизвестную отправку не повторять. Повтор — только `ops/TOPVIEW-RETRY.md`. Второй клик в той же попытке не разрешается. Другая независимая готовая сцена может занять реально свободный слот после полного скана. После отправки заново пересчитать все слоты и продолжить доступное.
6. Снять только точную собственную lease. Даже просроченный замок, уже заменённый другим, освобождать нельзя. Проверки работают при соблюдении протокола каждым исполнителем; Topview GUI не предоставляет серверный fencing token, поэтому это не безусловная гарантия против произвольного повторного нажатия.

## Общий CAS, если Dot и Grok оба работают · 16.11.2026

Порядок пробуждения — `ops/PRIMARY-BACKUP-WAKE.md`: первым будят Dot, Grok подключается резервом. Правило ниже — защита от гонки, если оба всё-таки работают: первый подтверждённый CAS выигрывает, второй не делает второй Create. Имя `ordinary` в holder — метка lease, не отдельный маршрут пробуждения. Прежняя формулировка «кто раньше успел» порядок пробуждения больше не задаёт. Исчерпание лимита Work — отдельное правило `ops/CONTINUE-PROTOCOL.md`: обычный ChatGPT сначала пытается запускать сам; если не может — запускает Grok Bot (резерв). Маршрут пробуждения остаётся прежним: первым Dot, резервом Grok.

Обязательный общий путь для **всех** исполнителей, включая Grok, Dot и старые часовые страховки:

1. На wake читать свежий main; при чужой действующей lease не делать ни claim, ни Create. Можно читать и готовить файлы, но такая подготовка не резервирует слот. После чужого освобождения/истечения не продолжать старую форму: начать сверку заново.
2. Полный live-скан всех досок и отдельная проверка конкретного item по полному нормализованному prompt, времени, входам и параметрам. Отсутствие записи в GitHub **не** доказывает отсутствия клика. Сохранить в scan `item_reconciliation[ITEM] = {"complete": true, "matched_task_ids": [], "ambiguous": false}` только после реальной сверки. Найденный task или неоднозначность запрещает новый Create этого item, даже если очередь ещё `waiting_for_slot`.
3. Взять точную собственную lease отдельным CAS/readback. `prepare-claim --item-id … --actor … --scan … --preflight … --source-sha <свежий main SHA> --write` проверяет общую очередь и готовит claim версии 2. Публиковать queue CAS с **тем же** expected main SHA. Только успешный CAS и readback определяют победителя. Проигравший перечитывает main и остаётся наблюдателем; force, слепой retry старого diff и отдельный параллельный реестр запрещены.
4. Только победитель после полного UI-preflight создаёт отдельный intent через существующий `prepare-intent`; queue и нужный ledger публикуются вместе CAS. Перед единственным Create перечитать main и выполнить `verify-before-create --item-id … --actor … --scan … --claim-id … --intent-id … --expected-payload-sha …` с собственными ID и SHA payload из текущего непрерывного исполнения. Новый helper проверяет точный опубликованный intent, lease, route, ledger и свежую дедуп-сверку. Он **не** разрешает replay: после разрыва исполнения, ошибки/таймаута Create или потери lease только reconciliation.
5. Резервный исполнитель не сбрасывает `claimed`, `submitting`, `submission_unknown` по TTL. Истечение lease разрешает получить редакторский замок для сверки, а не повторить отправку. Подтверждённый task записывается как уже отправленный; повтор только по `ops/TOPVIEW-RETRY.md`. Независимый следующий готовый item можно взять только после новой полной сверки и по очереди.
6. После отправки сохранить task ID/receipt и снять только собственную lease. Без подтверждённой записи результат объявлять `receipt_not_saved`, не «всё синхронизировано». Для простого read-only скана не держать глобальную lease на время браузера: брать её только для короткой записи квитанции или реальной launch-транзакции.

**Проверка внедрения:** наличие этого текста и тестов не доказывает, что независимый Grok уже прочитал и применяет его. Требуется его собственная квитанция с версией протокола и проверкой отказа при чужой lease/чужом claim, без реального Create. До такой квитанции не заявлять полную межагентную гарантию. В Topview GUI нет серверного idempotency/fencing token: соблюдающим протокол исполнителям общие CAS/intent предотвращают гонку, но произвольный ручной или обходной клик технически не запрещают. Не менять доступ/учётные данные ради этого без отдельного разрешения.

CLI готовит только локальные данные. Проверку ожидаемого SHA выполняет публикация GitHub, не Python helper. Корень локальной проверки должен быть снимком того же fresh main. Сканы и UI-проверки не синтезировать. Успешная проверка `verify-before-create` не является многократно используемым разрешением или самостоятельным браузерным действием.

## Minimax — отдельный peer, роль read-only · 18–19.11.2026

Решение владельца 19.11.2026: «1 да. 2 read-only. 3 read-only. 4 да». Minimax зарегистрирован в `ops/slot-backup.json` как **отдельная** surface со своим holder (`minimax:<UUID4>`), своим transport и своим запретом на запуск. Он **не** наследует ни Grok-окно :10–:40, ни Grok wake-issue, ни standing owner command, ни Grok lease, ни Grok retry policy и ни один счётчик.

- **Роль — только чтение.** `peers.minimax.role = "read_only"`, `peers.minimax.enabled = true`. Peer читает канон, очередь, статусы, отчёты и `ops/owner-tasks.json` и отвечает владельцу в Slack. Запрещённый список — в `peers.minimax.forbidden`: `claim`, `lease`, `intent`, `create`, `retry`, `cancel`, `queue_edit`, `budget_spend`, `site_submit`, `ledger_row`.
- **Путь launcher-а закрыт навсегда.** `minimax_launcher.enabled = false` и не меняется без отдельного решения владельца. Любая попытка пойти по пути launcher-а возвращает `minimax_launcher_disabled`. Чтобы открыть роль launcher-а, нужно в том же коммите вернуть `minimax` в `run_ledger.required_surfaces` и обеспечить настоящий `provider_run_id`.
- **Runtime run ID не требуется.** Read-only peer не делает попыток отправки, не пишет строку журнала и не создаёт intent, поэтому правило `provider_run_id` к нему не относится. Гвард `minimax_runtime_run_id_must_not_be_local_uuid` продолжает действовать для пути launcher-а.
- **Ledger.** `minimax` **не** входит в `run_ledger.required_surfaces`: журнал записывает реальные попытки отправки, а read-only peer их не делает. Пустые строки в журнал не дописываются.
- **Свой transport.** `actor.transport` обязан входить в `minimax_read_only.transport` (`minimax_transport_mismatch`) — список `["interactive_chat", "slack"]`.
- **Команда из Slack разрешена** (решение владельца 19.11.2026): сообщение в `#all-vint` с упоминанием `<@U0CJWT05HBM>` — прямая команда владельца, но только на чтение и ответ. `kind=owner_read`; гвард — `check_minimax_read_only_route`.
- **Доставка и ACK.** Задачи адресуются `to: "minimax"` в `ops/owner-tasks.json`, читаются `scripts/minimax_inbox.py` (только чтение, без wake и Create). Квитанция Slack-транспорта — `reports/slack-events.json`; `reports/topview-minimax-cycle.json` зарезервирован под путь launcher-а и не используется.
- **Ограничение доставки.** Список исполнителей на сайте (`scripts/robot_site_actions.py`, `scripts/canon_health.py`) пока знает только `claude`, `chatgpt`, `grok`, `any`. Задача, адресованная `minimax`, через сайт не маршрутизируется; её нужно заводить в `ops/owner-tasks.json` напрямую, либо сначала расширить список исполнителей на сайте отдельным владельческим решением.
- **Запрещённые пути.** Платный Topview MCP/Canvas и Plugin остаются запрещены: генерация по этому пути не Unlimited и тратит кредиты. Канонический путь — сайт под входом владельца, Unlimited0. Чтение Topview через MCP допустимо.

Регрессы-тесты: `tests/test_minimax_peer.py`, `tests/test_slack_transport.py`.

## «Продолжай» передаёт ответственность сменщику

После D7/полного приёма из `ops/CONTINUE-PROTOCOL.md` новый чат принимает **ту же незавершённую задачу заполнения слотов** `TOPVIEW-SLOT-PRIORITY-20261024`, а не создаёт её заново. Он читает реестр роли, текущий checkpoint/register, живые task IDs и открытые решения владельца. Порядок пробуждения эта передача не меняет (`ops/PRIMARY-BACKUP-WAKE.md`).

Под собственным общим замком/CAS сменщик своей среды (`ordinary` или `work`) записывает новый `session_id`, увеличивает только `foreground_owners.<surface>.epoch`, сохраняет прежнего владельца в историю, свой настоящий conversation ID либо `null` с причиной и первую проверенную стадию. Другой интерактивный исполнитель той же среды после такого переключения остаётся только читателем. Действующую чужую lease это не отбирает; сначала дождаться её освобождения/истечения и сверить результат. Неизвестные Create, claims, очередь и материалы наследуются без сброса. Неизвестную отправку не повторять; повтор — только `ops/TOPVIEW-RETRY.md`. Повторное «Продолжай» в том же принятом чате не создаёт ещё одну смену.

**Смена рабочего разговора не требует новой автоматизации.** Существующие независимые расписания читают тот же GitHub и продолжают работать. Реальная замена фонового задания — отдельный проверяемый переход: подготовить новый обычный исполнитель без отправок, проверить его реальный вызов, атомарно сменить `active_automation_id` и список разрешённых peer IDs с увеличением `route_generation`, затем выключить старый экземпляр. Неподдерживаемое API-перемещение в произвольный conversation ID не выдумывать; одну смену указателя не называть переносом платформенной подписки.

## Конечный batch одного пробуждения · 08.11.2026

Владелец t355u на вопрос «поднять лимит отправок на одно пробуждение, чтобы свободные слоты заполнялись сразу?» ответил «Да». t356u отдельно спросил, идёт ли запуск по очереди и берут ли связанные сцены отрывок прошлого ролика: да, это остаётся обязательным.

Живые поля: `grok_launcher.slot_capacity = 6` и `grok_launcher.max_submissions_per_wake = 6` в `ops/slot-backup.json`. Шесть — штатная ёмкость аккаунта, не произвольный большой лимит. Одно настоящее пробуждение (один `provider_run_id`) может поставить по одному Create на каждый реально свободный слот, пока есть готовые пункты и не достигнут этот потолок. Перед каждым Create — новый полный скан. Выбор — `wake_selection`: приоритет очереди, только `waiting_for_slot` с готовностью `ready`. Связанный пункт без материализованного отрывка (`@Video` / `source_item_id` / `previous_part_end`, файл+SHA или сохранённый private id+SHA) пропускается; `depends_on_*` само по себе отрывком не является. Следующий независимый готовый пункт занимает слот. `submission_unknown`, уже израсходованный item и содержательный отказ (код 7000, в том числе S49A) не перезапускаются этим решением. Старые строки журнала без `submissions` не расширяются. Новый `provider_run_id` не поднимает потолок текущего пробуждения. Prompt routine `topview-grok` уже требует заполнять свободные слоты и читает эту policy; отдельная правка routine не требуется.
