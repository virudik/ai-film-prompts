## Контрольные точки до и после крупной задачи (владелец, 19.10.2026)

Правило действует для ChatGPT, Claude, сменщика и работы по расписанию. Крупная задача — многошаговая или длительная работа, аудит, восстановление, пакет правок, изменение автоматики либо работа, которую нельзя надёжно завершить одним коротким действием.

**До начала выполнения** сохранить в GitHub main исходную контрольную точку: цель и команду/разрешение владельца, границы задачи, подтверждённое исходное состояние со ссылками или SHA, что уже сделано, план этапов, зависимости и известные блокеры, ближайший конкретный шаг. Использовать те же `reports/current-work-checkpoint.md` и `work-resume-register.json` (стабильный ID работы). Сначала коммит и read-back, затем первый длительный или изменяющий состояние этап. Предварительный checkpoint обозначает план, а не выполненную работу.

**После каждого существенного этапа и после завершения** обновить эти же файлы: фактически выполненное, сохранённые артефакты и commit/task ID, результаты проверок, что осталось, блокеры и точное место продолжения. Результат этапа и его запись сохранять в одной согласованной транзакции, где это возможно; успех объявлять только после read-back. Перед паузой, передачей смены или следующим длительным этапом сначала сохранить уже достигнутое. Новые важные решения и находки также фиксировать по правилам хендофа, не оставлять только в переписке.

Короткое чтение, ответ на вопрос или сама запись checkpoint не требуют отдельной рекурсивной контрольной точки. Существующий актуальный checkpoint можно дополнить; дубликаты файлов не создавать. Замок канона и CAS обязательны по действующим правилам. Если сохранить исходную точку не удалось, не объявлять её сохранённой и не начинать зависимый крупный этап; сообщить конкретный блокер. После сбоя продолжать с первой фактически незавершённой стадии, сверив живое состояние.

## Проверяемая точка продолжения (владелец, 27.10.2026)

`work-resume-register.json.resume_focus` — явный указатель задачи Серёгиуса для команды без уточнений. Писатель ставит его при принятии конкретной работы владельца; после завершения явно переводит на оставшуюся подтверждённую работу. Часовой монитор, Relay и простое обновление `updated_at` фокус не меняют. Конкретная новая команда владельца важнее указателя; `--work-id ID` выбирает её для проверки. Если фокус устарел, агент сначала восстанавливает его по канону после полного приёма; вопрос владельцу — только при реальной неразрешимой неоднозначности. Другие проекты используют свои хендофы/регистры; корневой указатель не переносить на них.

У незавершённой выбранной записи `recovery` содержит: последний доказанный этап, следующий шаг, время проверки, точный заголовок раздела `reports/current-work-checkpoint.md`, SHA-256 нормализованного раздела и SHA-256 файлов-доказательств, список чтения под задачу. В разделе обязателен `work_id: ID`. Последующий монитор может добавить свой раздел сверху, не ломая привязку. При изменении результата/следующего шага обновлять recovery в той же транзакции. Нельзя просто переписать SHA, чтобы скрыть расхождение: сначала проверить сам результат.

После проверки этапа писатель под собственным замком вызывает:
```sh
python3 scripts/resume_state.py . --capture WORK_ID --anchor '# Точный заголовок этапа' --last-completed 'Подтверждённый результат' --next-action 'Конкретный следующий шаг' --evidence reports/result.json --read-next ops/CONTINUE-PROTOCOL.md --focus
```
`--focus` нужен только при намеренной смене текущей работы. Скрипт пишет локальный реестр; он не выполняет push, не проверяет художественное качество и не заменяет read-back. Контрольная точка, результат и запись — один CAS-коммит. Незавершённые разделы с recovery-привязкой недельная чистка сохраняет; исторические дубли переводятся в `continuation_work_id`, прежняя запись дословно уходит в архив. Обязательства не закрываются переносом.

`scripts/continue_preflight.py` проверяет точный состав8источников,15якорей, полную SHA-256 копии `shadow/current-checkpoint.md`, уникальную открытую задачу, связанный раздел checkpoint и доказательства. Отсутствие/подмена любого из них запрещает короткий приём. `--require-short` возвращает ненулевой код при ошибке; обычный режим возвращает честный full-fallback. По умолчанию выводятся краткие записи, `--include-work` — полный реестр. Зелёный preflight подтверждает локальную возможность восстановления, а не живую авторизацию.

## Компактный пакет и индикатор

`scripts/build_resume_packet.py .` создаёт `shadow/resume-packet.md/.json`: выбранная задача и её точный раздел,15инвариантов, следующий шаг, файлы для чтения, SHA источников, существующие task IDs и отправки с неопределённым итогом. Слоты, решения владельца, замок и доступы всё равно проверяются заново. Пакет — производный навигатор, не восьмая инструкция и не новый мастер; весь исторический реестр и полный master в ответ скрипта не выгружаются. Проверку байтов можно выполнить программно, читая моделью только нужные разделы. Полный приём при изменении правил/сбое/сомнении остаётся обязательным.

Пакет строит **существующий** `shadow-brief.yml` после изменений исходников; нового расписания нет. При конфликте push workflow получает новый main и пересчитывает всё, не переносит устаревший готовый пакет через rebase. Только изменение содержимого создаёт коммит; собственные generated-файлы повторный запуск не вызывают. Экспорт `library-snapshot.yml` включает пакет и рабочий checkpoint из того же checkout.

На странице каждого из пяти проектов «↪ Продолжение» показывает выбранную работу, сохранённый этап, следующий шаг, дату проверки и размер стартового пакета. Браузер сверяет SHA опубликованных источников; несовпадение/404/ошибка сети/неверное время — «нужна проверка». Это не счётчик остатка контекста ChatGPT и не разрешение на генерацию. У каждого проекта собственный пакет, ссылка и журнал приёма. При отсутствии задачи показывается «готово · ждёт владельца», а не выдуманная текущая работа.

## Продолжение после обрыва и проверка

- Сохранён task ID — проверить существующую задачу; даже ошибочный waiting-флаг не разрешает повторить Create.
- Есть claim / submitting / submission_unknown либо submitted без task ID — сначала сверить внешнее состояние и восстановить квитанцию. Автоматического повтора нет. Архивные task IDs тоже учитываются.
- Этап и доказательства уже сохранены — переходить к следующему; повторный «Продолжай» сам по себе не пишет реестр и не вызывает внешних действий.
- Готовый waiting-item — только кандидат: обязательны свежие общий скан слотов, точные входы/QC, Unlimited0 и CAS по `ops/TOPVIEW-FREE-LAUNCH.md`. Заблокированный пункт не удерживает свободный слот.

Тесты `tests/test_continue_recovery.py` проверяют повреждение/потерю checkpoint, доказательства, неоднозначный фокус, новую запись монитора, обрыв после claim/отправки, сохранённый task ID, повторное чтение и недельную чистку. `tests/continue_status_check.js` проверяет состояния индикатора. Это тесты механизма в изолированной среде; фактическое исполнение нового Project-чата по одному «Продолжай» отмечается отдельно и не выводится из установки настроек. Откат улучшения: восстановить прежний проверенный код/правила из git; при ошибке всегда полный приём, история и канон сохраняются.

## Как новый чат распознаёт именно одно слово

В `USER-GUIDE.md` (раздел «2. ChatGPT Project») содержится точный текст Project Instructions с явным триггером `КОМАНДА «ПРОДОЛЖАЙ» (D7)`. Первый входной указатель — эта инструкция Project, после чего читаются `NEW-CHAT-HANDOFF.md` и данный протокол. **Сам GitHub не обновляет настройку Project Instructions в ChatGPT.** Пока новая строка не сверена в интерфейсе, статус активации триггера в самом Project — `unverified`, даже если код и документация в `main` исправны. При сомнении новый чат может безопасно выполнить общий D7-takeover по текущим настройкам проекта.

ChatGPT не предоставляет здесь управляемую агентом команду сжатия/восстановления скрытого контекста **того же самого** бесконечного чата, не умеет программно сбрасывать Chat/Work лимиты и не гарантирует сохранения всех деталей старой переписки. D7 + регистрация работы решает практическую **передачу**, а не бесконечную жизнь UI-чата. Claude может поддерживать более длинную непрерывную сессию собственным механизмом compaction, но внешняя память в GitHub всё равно надёжнее для канонических решений.

## Квитанция реального приёма смены (владелец, 27.10.2026)

Принимающий чат после живых проверок и **первого фактического действия** сохраняет квитанцию своего проекта. Она обязательна при передаче работы новому чату, а не при каждом часовом опросе. Сохранить её в том же CAS-коммите, что и checkpoint первого шага, под собственным замком проекта; прочитать обратно. До успешного push/readback не объявлять приём записанным. При недоступной записи — сообщить конкретно `receipt_not_saved`, не подделывать подтверждение. Готовность пакета и миграция проекта квитанций не создают.

Квитанция содержит:
- `receipt_id` — уникальный ID этого приёма; повтор с тем же ID и содержимым ничего не пишет, другое содержимое — ошибка, историю не переписывать.
- `project`, `work_id`, точный `source_head` свежего checkout; скрипт добавляет SHA проверенных источников, время записи и `execution_authorized: false`.
- `chat`: `agent` (точный holder замка), понятный `label`, `session_id` текущего запуска; при доступном реальном ID/URL чата — `chat_id`, `identity_status: verified` и `identity_evidence` (откуда взят). Если среда не раскрывает ID — `chat_id: null`, `identity_status: unavailable`. Локальный session_id не называть ID чата, ссылку старого share не выдавать за текущую. Точная идентичность тогда честно остаётся неподтверждённой.
- `started_at`, `accepted_at`; семь `checks` с `id`, `result: passed|blocked` и конкретным `evidence`: `fresh_main`, `instructions`, `checkpoint`, `owner_inbox`, `owner_decisions`, `capabilities`, `project_lock`. «Проверено» без того, что прочитано/наблюдалось, недостаточно. Живые проверки выполняет агент; скрипт проверяет структуру и локальную привязку, не имитирует доступ к сервисам.
- `outcome: accepted|waiting_for_owner|blocked`; `first_action` содержит `at`, `description`, `state: started|completed|waiting|not_started` и `evidence` (артефакт, checkpoint или факт ожидания). Запланированный будущий шаг не выдавать за начало исполнения. Заблокированная проверка не позволяет outcome accepted. В ожидании владельца не создавать искусственную работу.

```sh
python3 scripts/handoff_receipt.py . --project kotmonavty --input /tmp/actual-takeover.json
```

Входной JSON агент составляет только из фактических наблюдений. Утилита не получает замок и не публикует сама. После локальной записи — сохранить согласованные исходники, пересобрать пакет, CAS-push, readback. Изменился HEAD/фокус — перечитать и пересоставить факт приёма, не менять проверенный SHA наугад. При полном чтении сначала восстановить конкретные пробелы и доказательства; пока preflight не проходит, возможна только blocked-квитанция.

На сайте видны последний принимающий чат/сессия, работа, время и первое действие; по ссылке — все проверки. Старый приём другой работы остаётся историей, не доказательством приёма текущего фокуса. Хранятся последние 20 квитанций, более старые целиком переносятся в `archive/reports/handoff-receipts.json` своего проекта до уменьшения живого журнала, оба файла в одной транзакции. ID проверяются и в архиве. Это ограничивает рабочий журнал без потери истории. Недельная проверка сверяет квитанции и не придумывает отсутствующие.

Проверка следующим реальным новым чатом остаётся отдельной: он должен сам прочитать источники, записать собственную квитанцию и выполнить разрешённый следующий шаг. Квитанция текущего внедряющего чата подтверждает только его собственный приём, не этот будущий тест.
