## Команда пользователя «Продолжай»

Новый чат/Work **в том же ChatGPT Project** самостоятельно выполняет:

1. Получить свежий `main` без вопросов пользователю. Прочитать `shadow/takeover-brief.md`, проверить `valid=True`, 15/15 ✓ и сверить хеши **с текущими байтами**, а не только с отметкой генерации (скрипт `python3 scripts/continue_preflight.py .`; при отсутствии локального git — эквивалент по GitHub API). При любом несовпадении выбрать полный приём 7 инструкций.
2. Прочесть `shadow/current-checkpoint.md` целиком, живые `project-status.json`, `topview-status.json`, `instruction-sync-status.json`, `automation-monitor-status.json`, `monitor-role.json`, `work-resume-register.json` и открыть актуальные `owner_decisions` в Supabase. `GitHub main` приоритетнее любой Library/Project/Drive копии.
3. Выбрать **последнюю всё ещё открытую конкретную работу** по `work-resume-register.json`, проверив её реальность по текущему GitHub/owner_decisions. Если пользователь дал в новом чате конкретную новую задачу — она приоритетнее регистра. Не придумывать выполненную работу или последний шаг только из времени сообщения.
4. Открыть только нужные полные разделы канона из D7 `read_sets`; перед правкой обязательно свежий HEAD. Не задавать вопрос, на который уже есть ответ. Однозначный безопасный следующий шаг выполнять без согласования. Перед оплатой, генерацией, одобрением, закрытием, удалением либо неоднозначностью Scene↔task — требовать подтверждённое решение владельца.
5. Перед началом крупной задачи сохранить исходный checkpoint по разделу «Контрольные точки до и после крупной задачи» ниже. После каждого существенного этапа работы коммитить минимальную актуализацию `work-resume-register.json` **в той же согласованной транзакции**, что и соответствующий материал или инструкцию: ID работы, последний доказанный результат, сделано, следующий шаг, референсы на commit/issue, владелец решения, блокеры и последняя проверка. Закрытую запись не держать как живую. Это точка восстановления после лимита без новой «простыни» хендофа.
6. Перед завершением текущей беседы или Work зафиксировать checkpoint последнего этапа и результаты проверок. При новом чате начать с шага 1, **не пересоздавать** планы и сцены. При недостатке информации сообщить конкретный пробел.

## Контрольные точки до и после крупной задачи (владелец, 19.10.2026)

Правило действует для ChatGPT, Claude, сменщика и работы по расписанию. Крупная задача — многошаговая или длительная работа, аудит, восстановление, пакет правок, изменение автоматики либо работа, которую нельзя надёжно завершить одним коротким действием.

**До начала выполнения** сохранить в GitHub main исходную контрольную точку: цель и команду/разрешение владельца, границы задачи, подтверждённое исходное состояние со ссылками или SHA, что уже сделано, план этапов, зависимости и известные блокеры, ближайший конкретный шаг. Использовать те же `reports/current-work-checkpoint.md` и `work-resume-register.json` (стабильный ID работы). Сначала коммит и read-back, затем первый длительный или изменяющий состояние этап. Предварительный checkpoint обозначает план, а не выполненную работу.

**После каждого существенного этапа и после завершения** обновить эти же файлы: фактически выполненное, сохранённые артефакты и commit/task ID, результаты проверок, что осталось, блокеры и точное место продолжения. Результат этапа и его запись сохранять в одной согласованной транзакции, где это возможно; успех объявлять только после read-back. Перед паузой, передачей смены или следующим длительным этапом сначала сохранить уже достигнутое. Новые важные решения и находки также фиксировать по правилам хендофа, не оставлять только в переписке.

Короткое чтение, ответ на вопрос или сама запись checkpoint не требуют отдельной рекурсивной контрольной точки. Существующий актуальный checkpoint можно дополнить; дубликаты файлов не создавать. Замок канона и CAS обязательны по действующим правилам. Если сохранить исходную точку не удалось, не объявлять её сохранённой и не начинать зависимый крупный этап; сообщить конкретный блокер. После сбоя продолжать с первой фактически незавершённой стадии, сверив живое состояние.

## Самостоятельное продолжение разрешённой очереди (владелец, 17.10.2026)

Владелец поручил продолжать подготовку, отслеживать освобождение слотов и запускать уже разрешённые задания без периодических сообщений «продолжай» и без повторного согласования каждого пункта. Это разрешение сохраняется при смене чата; подтверждённые границы берутся из свежих `ops/topview-launch-queue.json`, `reports/current-work-checkpoint.md`, `work-resume-register.json` и новых решений владельца. Новый чат после приёма сам выполняет следующий доступный шаг. Ожидание слота не означает завершение задания.

- Существующая задача **AI Film — готовые сцены по слотам**, ID `6acae6ab433481919e88665c520b8ef2`: проверка раз в час, HH:55 Europe/Moscow. При приёме проверить её реальное состояние и актуальность prompt через Automations. Не создавать новый watcher и не включать архивные мониторы. Состояние enabled само по себе не доказывает успешный цикл или вход в браузере.
- Активный чат выполняет доступные шаги сейчас; между сообщениями проверку запускает именно существующая automation. Текст инструкции не создаёт вечный фоновый процесс, не переносит браузерный вход и не пробуждает новый чат автоматически. Новый чат/сменщик принимает ту же работу по D7/полному приёму, проверяет capabilities и продолжает её с checkpoint.
- Перед канонической записью или запуском проверить `ops/canon-lock.json` по `ops/CANON-LOCK.md`: чужой действующий замок не обходить; свой взять и освободить в конце. Явные исключения для входящих задач/их архива и отметок референсов — в том же протоколе.
- `claim.run_id` запуска из задачи по расписанию начинается с `chatgpt-scheduled-`, из рабочего чата — иначе (например `chatgpt-cloud-`). По этому признаку ежедневная проверка `launch-autonomy-check.yml` (08:30 МСК, `reports/launch-autonomy.json`) отличает самостоятельные запуски и пишет в issue `topview-events`, если свободные слоты простаивали.
- При свободных слотах выполнить готовые разрешённые items по приоритету и зависимостям, после каждого запуска пересчитать слоты; не останавливаться после первого item при наличии места. Для каждого — полный свежий скан, anti-duplicate, точные prompt/input SHA, видимый Unlimited/цена 0, атомарный CAS-claim, один Create, подтверждённый task ID и receipt. Только сайт через разрешённый встроенный браузер; платный MCP/Canvas запрещён. Порядок действий — `ops/TOPVIEW-FREE-LAUNCH.md`.
- В каждой фоновой среде отдельно проверить доступ к браузеру и вход. Если общий доступ/импорт отсутствует, сохранить конкретный blocker, уведомить владельца один раз и приостановить только затронутую фазу отправки до восстановления; продолжать независимые задачи, проверки и чистку. Всё часовое задание выключать только по новой явной команде владельца. Один заблокированный item не мешает независимым готовым items. Временный сбой чтения не выдавать за заполненную очередь или успешную проверку.
- Ранее данное разрешение не спрашивать заново. Новое решение требуется для расширения объёма, платного пути, неразрешённого повторного рендера, редакционной приёмки/удаления и творческой неоднозначности. Точный выбранный объём и действующие согласования брать из свежей очереди; отменённую задержку после одного теста танца не восстанавливать.
- Уведомлять о подтверждённых запусках, существенных новых блокерах, запросе необходимой оценки и завершении очереди. Одинаковые проверки заполненных слотов не дублировать. **Новый подтверждённый Relay event_id требует квитанции даже при no_update** по `ops/TOPVIEW-EVENT-WAKE.md`; завершённый дубль не писать. **Обычный цикл без изменений — без коммитов** (владелец 23.10.2026): если нет нового запуска, результата, задачи, блокера или сбоя, замок не брать и checkpoint / register не писать. Есть изменение — замок, один коммит с данными (замок снимается в том же коммите, `ops/CANON-LOCK.md` п. 5). Старые записи checkpoint / register / очереди уходят в архив при недельной чистке (`NEW-CHAT-HANDOFF.md` «Как чистить», п. 8). После существенного шага и перед паузой сохранять результат/receipt и те же checkpoint/register в main с read-back. Не переписывать исторические submitted-промпты, не подделывать heartbeat. Робот телеметрии остаётся отдельным основным писателем своего домена; запуск очереди не даёт права перехватить его роль.

## Как новый чат распознаёт именно одно слово

В `USER-GUIDE.md` (раздел «2. ChatGPT Project») содержится точный текст Project Instructions с явным триггером `КОМАНДА «ПРОДОЛЖАЙ» (D7)`. Первый входной указатель — эта инструкция Project, после чего читаются `NEW-CHAT-HANDOFF.md` и данный протокол. **Сам GitHub не обновляет настройку Project Instructions в ChatGPT.** Пока новая строка не сверена в интерфейсе, статус активации триггера в самом Project — `unverified`, даже если код и документация в `main` исправны. При сомнении новый чат может безопасно выполнить общий D7-takeover по текущим настройкам проекта.

## Что нельзя автоматизировать одной настройкой

ChatGPT не предоставляет здесь управляемую агентом команду сжатия/восстановления скрытого контекста **того же самого** бесконечного чата, не умеет программно сбрасывать Chat/Work лимиты и не гарантирует сохранения всех деталей старой переписки. D7 + регистрация работы решает практическую **передачу**, а не бесконечную жизнь UI-чата. Claude может поддерживать более длинную непрерывную сессию собственным механизмом compaction, но внешняя память в GitHub всё равно надёжнее для канонических решений.
