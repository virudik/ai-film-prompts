# Робот пишет телеметрию Topview (вместо ИИ-монитора) — состояние и переключение

Статус: действует. Проверено: 18.10.2026.

**Статус 13.10.2026 (решение владельца «пускай робот всё делает»): робот — ОСНОВНОЙ писатель телеметрии** (`monitor-role.json: primary=robot`, `standby=chatgpt`). Суточная параллельная проверка пропущена по решению владельца; перед включением боевой режим прогнан сквозным тестом на копии репозитория с реальными данными (публикация, повтор → `noop`, завершение задачи, `health=ok`). Решение владельца: рутинный мониторинг переносится в робота, чтобы проект не зависел от расписаний Claude и ChatGPT.

## Что делает робот
`topview-robot.yml` (запуск каждые 10 минут снаружи, `ops/ROBOT-TRIGGER.md`): `scripts/topview_api_scan.py` сканирует Topview (только GET), затем `scripts/robot_telemetry.py` решает, что публиковать:

| Решение | Когда | Действие |
|---|---|---|
| `noop` | ничего не изменилось, телеметрии меньше 50 минут | ничего |
| `publish` | новая / завершённая / сменившая статус задача, либо телеметрии 50+ минут (пульс до «устарела» на 105) | в ОДНОМ коммите: `topview-task-map` → журнал → `topview-status` → `review-ledger` (только `result_received`) → `topview-checkpoint` (последним); если нужно, минимальная правка slow-строк master (`master_slow_edit.apply_plan`) и `SYNC-TRIGGER.txt`; перед коммитом `build_project_status` обязан дать `health=ok`; затем запись цикла `runner=robot` в `automation-monitor-status.json`, push с проверкой (CAS), read-back |
| `hold` | скан неполный (`detail_failed`), известная задача исчезла, задача без сцены, сцена не в master | НИЧЕГО не публикует; один раз пишет честный `degraded`-цикл и сообщение в ленту событий |
| сбой проверки публикации | валидатор статуса или журнала отклонил подготовленную публикацию | телеметрию не пишет; один раз (повтор не чаще 50 мин) записывает `degraded`-цикл `publish failed: …` в `automation-monitor-status.json` и одно событие в ленту (16.10.2026; раньше сбой был молчаливым) |

Перед проверкой журнала робот добавляет **пустые** строки `review-ledger.json` для новых активных сцен (решения владельца не выводятся). Код подсцены (A1…B10, «часть N») хранится в `topview-status.active_tasks[].part`, `topview-status.task_parts` и `topview-task-map.processed_tasks[].part`; новая строка slow — `| 28 · B6 · Танец 6 — … |`.

Чего робот не делает никогда: не запускает, не одобряет, не перезапускает, не удаляет, не тратит кредиты, не создаёт Scene ID, **не снимает canonical slow** (только кнопка владельца), не угадывает привязку «задача → сцена» (принимает только точное или нормализованное совпадение промта ровно с одной активной сценой, `topview_prompt_match`).

Оповещения владельца: одна «лента» — открытый issue с меткой `topview-events`, каждое событие комментарий (результат готов + свободные слоты; задача без сцены; сбой). Дубли гасятся по `automation-monitor-status.notification_state.robot_notified_keys`.

## Режимы
GitHub Variable `ROBOT_TELEMETRY` (Settings → Secrets and variables → Actions → Variables):
- нет переменной или `on` — **сейчас**: реальная публикация, **и только если** `monitor-role.json: primary == robot` (`scripts/monitor_role.py --me robot`); иначе «не писатель», запись отказана. (С 13.10.2026 workflow по умолчанию `on`, чтобы владельцу ничего не нужно было ставить.)
- `shadow` — **аварийный выключатель**: пишет только `shadow/robot-cycle-preview.json` (что бы опубликовал). Канон не затронут.

## Как проверяли бы перед переключением (не выполнялось: владелец 13.10 решил включить сразу; пригодно для разбора сбоев)
1. В `shadow/robot-cycle-preview.json` каждое событие `publish` с `new`/`finished` совпадает с тем, что монитор опубликовал в течение ~70 минут; нет `publish`-расхождений, которых монитор не сделал.
2. Нет неожиданных `hold`; все `hold` объяснимы (например, задача без сцены, о которой владелец знает).
3. `shadow/topview-robot-status.json → comparison` без расхождений, не объяснимых отставанием монитора.
4. Тесты: `tests/test_robot_telemetry.py` (21), `tests/test_monitor_failover.py` (роль `robot`).

## Переключение (выполнено 13.10.2026 по решению владельца)
1. `monitor-role.json`: `primary=robot`, `standby=chatgpt` (ChatGPT остаётся с `chatgpt_writer_eligible=true`: если у робота нет ПОДТВЕРЖДЁННОГО здорового цикла 180 минут, резерв подхватит сам — страховка).
2. `ROBOT_TELEMETRY`: ставить не нужно — без переменной workflow работает как `on`.
3. ChatGPT-монитор по проверке роли начинает выдавать `skip`; он не пишет. Claude-монитор остаётся выключенным.
4. Первые сутки смотреть: цикл `runner=robot_scheduled_task` с `health=ok` в `automation-monitor-status.json`, чип «Монитор» на сайте, отсутствие `monitor-alert`.

**Откат (если робот «косячит»):** владелец ставит GitHub Variable `ROBOT_TELEMETRY=shadow` (Settings → Secrets and variables → Actions → Variables → New repository variable) — робот сразу перестаёт писать; и/или команда «основной монитор — ChatGPT» → любой агент меняет `monitor-role.json: primary=chatgpt, standby=robot`. Формат файлов телеметрии не меняется. Если робот 180 минут без подтверждённого здорового цикла, ChatGPT подхватит сам и станет основным; обратно робот вернётся только по команде владельца.

**Починка устаревших строк master (13.10.2026).** Если задача уже записана в `topview-task-map.processed_tasks` как завершённая, а строка в таблице «⏳ Сейчас в медленной генерации» всё ещё показывает `init`/`running`, робот один раз переводит строку в «✅ Технический результат получен» (или ошибку), добавляет одну техническую строку в карточку сцены и пересчитывает шапку по **реальным** занятым слотам Topview. Canonical slow не снимается (только кнопка владельца). При первом боевом запуске так чинятся строки сцен 25, 27, 30, 31 (их задачи завершились 12–13.10, а строки остались `init`; шапка мастера показывала 6/6 вместо 2/6). `master_slow_edit.py` больше не ставит второй жёлтый маркер, если в карточке уже есть маркер с техническим хвостом.

## Что робот пока НЕ заменяет (остаётся за человеком/агентом, редко)
- Привязка новой задачи, не совпавшей точно ни с одним промтом (робот держит `hold` и пишет в ленту).
- Текстовые `owner_task` (творческие и неоднозначные), `tv_mark_status(result_ok)` как автоприменение, «Не нужна» при зависимых сценах.
- Суточная глубокая проверка семи инструкций на противоречия (после зачистки её заменяют тесты и 15 якорей; ИИ-часть опциональна).
- Копии в Notion / Library / Claude Project (best-effort, не обязательны для канона).

## Пробелы в ссылках Topview и остановка публикации (23.10.2026)

Если сканер работает, но сайт показывает устаревшие данные, сначала читать `automation-monitor-status.json.last_scheduled_cycle.note`. При `hold: unmapped_active` сравнить полный сохранённый `parameters.positivePrompt` задачи с каноническим блоком и квитанцией запуска. Нельзя обновлять `checked_at` вручную или скрывать предупреждение.

Для 58P1 Topview сериализовал `@Image3/@Image4` как `<<<Image3>>> /<<<Image4>>>`. Квитанция и живые параметры совпали полностью, но прежний matcher не нормализовал пробелы возле `/`. Исправлен `topview_prompt_match.normalise`: удаляет только пробелы вокруг `/`, `–`, `—` **между двумя токенами Image/Video/Audio**. Символ-разделитель, номера и порядок ссылок, текст промпта остаются значимыми. Требование полного exact/normalized совпадения с единственной активной сценой сохранено; близость текста недостаточна. Регрессионный тест использует фактическую квитанцию 58P1 и проверяет отказ при смысловом изменении.

После исправления нужен настоящий успешный цикл робота с новой телеметрией, совпадением активных task ID и публикацией Pages. Зелёный workflow сам по себе недостаточен: робот может завершить workflow успешно с `hold`.

Workflow робота получает полную историю (`actions/checkout`, `fetch-depth: 0`) и актуальную ветку (`ref: github.ref_name`). При depth 1 `git log -- <telemetry paths>` ошибочно считает граничный коммит изменившим все файлы: даже исправление скрипта агентом блокировало робота на 50 минут. Полная история сохраняет защиту от настоящих параллельных записей; queued-запуск читает свежую ветку, чтобы не перебазировать старый скан поверх нового.

## Архив операций (26.10.2026)

`topview-operation-journal.json` сохраняет последние `retention_max_events` (500) операций. `scripts/operation_journal.py` переносит более ранние записи целиком в `archive/ops/topview-operation-journal-archive.json` в исходном порядке, включая одинаковые события. Архив создаётся при первом превышении; `events_archive` и `archived_event_count` указывают путь и точное число перенесённых записей. Данные задачи/слота берутся из task-map/status, не из архива.

Оба писателя (`monitor_publish.py` через robot_telemetry и `robot_master_actions.py`) публикуют архив и рабочий журнал в одном CAS-коммите. Архив записывается первым, рабочий файл вторым; конфликт смещения/содержимого останавливает обрезку. После отклонённого push перечитать main и пересчитать, не переигрывать старый архив. Прерывание между записями безопасно повторяется; совпадающие события не теряются и пакет не размножается. Агент, дописывающий журнал вручную, обязан соблюдать тот же контракт. Отдельного расписания или очистительного коммита нет. Тесты: `tests/test_operation_journal.py`.
