# Служебные файлы и хендоф — автоматика чистки

Статус: действует с 11.11.2026. Проверено: 11.11.2026.

Решение владельца 11.11.2026 (04:10 МСК). Робот — `.github/workflows/service-maintenance.yml`.

## Регистр и прочие служебные файлы

Раз в сутки (07:40 МСК) и когда `canon-health.json` содержит предупреждение `service-file-size`, робот запускает:

```
python3 scripts/trim_service_files.py . --write --skip-held-locks
```

Скрипт переносит в архив только законченные записи (завершённая работа, старые пункты `done` / `completed`, завершённые элементы очереди по правилам шапки скрипта). Активную работу он не трогает. Если общий замок или замок проекта ещё держится и не истёк, этот проект пропускается. Изменение коммитится в `main`. Хендофы этот запуск не режет.

## Хендоф

Предупреждения `handoff-size` и `project-handoff-size` робот **не** чинит коммитом в `main`. Он готовит отдельный PR (`scripts/propose_handoff_trim.py`): старые датированные блоки переносятся дословно в `archive/handoff-log.md` (у проекта — в его `archive/handoff-log.md`). Блок «СЕЙЧАС» и правила остаются.

Перед вливанием проверяющий сверяет перенос с текущим состоянием: каждый уносимый блок должен быть действительно устаревшим. Всё, что ещё актуально или важно, нужно вернуть в хендоф. Робот этот PR не вливает.

Уведомление уходит в тот же канал, что и предупреждение «Здоровье канона»: Agent Relay, адрес `site_alert_address` из `ops/relay-wake.json`. В тексте PR и в уведомлении есть обязанность проверить блоки до вливания. Повторный PR не открывается, пока предыдущий с ветки `robot/handoff-trim` ещё открыт.
