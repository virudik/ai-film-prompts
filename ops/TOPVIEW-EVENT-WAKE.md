## Технические повторы и продолжение очереди · 30.10.2026

## Временный сбой браузера (владелец, 27.10.2026)

По команде владельца при временном сбое доступа/чтения браузера **до Create** выполнить в том же запуске ещё **1–2 попытки** с паузой **около минуты** между ними (до 60 секунд за одну паузу). Повторять только доступ и чтение/скан; это не повторная отправка генерации. Подтверждённое отсутствие браузера, входа или нужного разрешения фиксировать конкретно, без бесконечного цикла и платного обхода.

После восстановления заново проверить свежий main, решения владельца, очередь/входы/QC, замок и все физические слоты по `ops/TOPVIEW-FREE-LAUNCH.md`. Исходный `observed_at` не обновлять искусственно: просроченное событие не разрешает Create. Сохранённый `task_id` означает проверку существующей задачи; `claim`, `submitting` или `submission_unknown` требуют восстановления фактического исхода. Неизвестный исход Create никогда не разрешает повторный клик.

Если повторные проверки не помогли, завершить подтверждённое событие квитанцией `outcome: blocked_browser`, `retryable: true`; сохранить фактические время/число попыток и причину, известные task/claim IDs и ближайший шаг в текущие checkpoint/register. Запись — по обычному общему замку/CAS/readback; чужой замок или сбой записи дают `receipt_not_saved`, без ложного ACK. Интерактивный чат не создаёт событийные квитанции от имени handler.

Следующее настоящее пробуждение либо существующее часовое задание HH:55 заново проверяет доступ и при восстановлении выполняет готовую разрешённую работу после полного свежего preflight, не ждёт повторного «Продолжай» или снятия временного blocker владельцем. Старый `blocked_browser` не удерживает слот и не заменяет свежий скан; уже отправленное не повторяется. Новых расписаний/задач, разрешений на повторные рендеры и изменений художественной приёмки это правило не создаёт.

## Ограничение журнала (владелец 26.10.2026)

В рабочем `reports/topview-event-wake.json` остаются максимум 100 явно завершённых событий с `checked_at` не старше 30 дней и **все незавершённые**. Только `retryable=false`, известный завершённый `outcome` и корректная дата не из будущего разрешают перенос; blocked, retryable, submission_unknown, неизвестный статус и ненадёжная дата остаются. Если один ID имеет незавершённую версию, сохраняются все его версии. Полные записи дословно уходят в `archive/reports/topview-event-wake-archive.json`; файл создаётся при первом настоящем переносе. Рабочий `archived_event_ids` хранит точные ID навсегда, `events_archive` указывает путь. Не обрезать этот индекс и не переносить диагностические `test_acks`/доказательства приёмки.

Очистка включена в существующий `scripts/trim_service_files.py`: обычный недельный запуск обслуживает и Relay. Обработчик после записи квитанции, под тем же canon-lock и до финального CAS-коммита, выполняет `python3 scripts/trim_service_files.py . --relay-only --write`. Этот режим не меняет очередь, другие проекты, checkpoint или register. Архив и рабочий отчёт публикуются вместе с квитанцией; дополнительных коммитов/расписаний очистки нет. Сначала записываются полные архивные данные, затем убираются рабочие детали; повтор безопасен, одинаковые архивные записи не размножаются. При ошибке не публиковать частичное удаление; сохранить квитанцию и старые данные, явно записать blocker. Без переноса архив вообще не загружается. Для no_update компактно обновлять текущую строку checkpoint/register, не дописывать длинную историю каждого сигнала.

Дедуп обработчика и robot `handler_acked` проверяют **точное** совпадение в `events[].event_id` или `archived_event_ids`, не подстроку по всему JSON. Архивный ID означает завершённую обработку: не восстанавливать событие в рабочем массиве и не запускать повторно. Противоречащая незавершённая live-запись — blocker, не автоматический повтор. Индекс сохраняет для робота подтверждение ответа после архивирования; `result:abc` не совпадает с `result:abcdef`. Журнал больше 200КБ вызывает штатное предупреждение canon-health и проверку очистки; незавершённые записи ради порога не удалять. Архив — история, не очередь запуска и не обязательное чтение сменщика.

Тесты: `tests/test_relay_retention.py`, `tests/test_slot_rewake.py`, `tests/test_trim_service_files.py` (включены в существующий integration workflow). Проверяются возраст/число, сохранение исходных данных, идемпотентность, сбой записи, точный поиск и отсутствие ложного предупреждения после архивирования. Рабочий events[] пока пуст: искусственные production-квитанции для демонстрации не создаются.

## Сигналы робота и эксплуатация

**Не терять сигнал после hold (26.10, Claude).** Если завершение задачи робот впервые увидел в цикле hold, результат объявляется (и попадает в `robot_notified_keys`), но ничего не публикуется. Раньше из-за этого Relay-сигнал терялся до часовой проверки. Теперь отправленные пробуждения учитываются отдельно (`notification_state.robot_wake_keys`), и сигнал уходит на ближайшей успешной публикации, один раз на результат. Тест: `test_result_first_seen_in_a_hold_still_wakes_on_the_next_publish`.

**Повторный сигнал и контроль ответа (26.10, Claude).** Первый сигнал робот шлёт при завершении задачи. Если после этого (или без завершения — отмена, пропавшая задача) слот остаётся свободным, а в `ops/queue-readiness.json` есть пункт с кодом `ready` или `prepare_continuity`, робот в noop/publish-цикле шлёт повтор с `event_id: slots:<эпизод>:<n>` (эпизод = набор активных задач всех проектов): не чаще раза в 20 мин после любого предыдущего сигнала и не больше 3 раз на эпизод, дальше — часовая проверка. Состояние — `automation-monitor-status.json` → `notification_state.robot_rewake`. Перед повтором робот ищет точный ID предыдущего сигнала в `reports/topview-event-wake.json` → `events[].event_id` или `archived_event_ids`; не нашёл — один комментарий в issue18 «исполнитель не ответил» (то же при ошибке/отсутствии ключа Relay). Обработчик обязан записывать в этот отчёт каждый обработанный event_id, включая `slots:…` и `no_update`; для `slots:` нет задачи-результата — это просто «слот всё ещё свободен». Тесты: `tests/test_slot_rewake.py`.

Транспорт: `scripts/relay_wake.py`, адреса/точная личность отправителя — `ops/relay-wake.json`, агентский токен — только GitHub secret `AGENT_RELAY_TOKEN`. HTTP2xx без `ok=true` и настоящего message_id не считается доставкой; стабильный Idempotency-Key, без redirect и подмены API origin. Транспортная квитанция не заменяет ACK обработчика. Ошибка Relay не останавливает телеметрию; фиксировать blocker. При смене ChatGPT inbox обновить конфигурацию и проверить доставку.

Рабочая связка: 10-минутный GitHub-робот → bot-issue с event_id → Relay DM → существующий handler `6adc585e7ac08191bb93825117dc7213`; часовой `6acae6ab433481919e88665c520b8ef2` HH:55 Europe/Moscow остаётся страховкой. Gmail-handler V2 и диагностический координатор выключены. Старые тесты без новой причины не повторять, дубли автоматизаций не создавать.
