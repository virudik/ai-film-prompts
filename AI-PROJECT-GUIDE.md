## 3. Master: как вести `video-prompts.md`

- Единственный master — `video-prompts.md` в `main`. Не создавать `v2`, `final`, `copy`, `final-final`.
- Перед каждой записью — `git pull` и чтение свежего master.
- Менять только нужную сцену и связанные оглавление / счётчики / статус / slow-метки. Минимальный diff.
- Scene ID стабильны и не перенумеровываются; закрытые ID не переиспользуются никогда. Актуальный список зарезервированных ID — `project-status.json.reserved_scene_ids` и строка «Сцены … удалены из active master» в свежем master; в этом файле список не дублируется.
- Если следующий Scene ID однозначно следует из свежего master, не спрашивать владельца — брать следующий новый стабильный ID. Новую сцену из Topview-задачи заводят только с согласия владельца.
- Готовая сцена убирается из активного master только по решению владельца, что результат принят и промт не нужен; `Topview success` для этого недостаточно.
- `NEEDS_FIX` и `NEEDS_RERENDER` не разрешают автоматическую переписку или перезапуск.
- Slow-сцены не перезапускать и не снимать с slow без результата, ошибки или явного решения владельца.
- Master — UTF-8 без BOM, только LF, не более одной пустой строки подряд (проверяет валидатор).

## 4. Как писать промты

Полный обязательный стандарт — `PROMPT-STYLE-GUIDE.md`. Перед новым или существенно переработанным промтом: прочитать его; свежий master; 1–2 близкие актуальные сцены; проверить engine, Scene ID и роли референсов; только потом писать.

Промт master-уровня обычно содержит: техническую строку; точные роли `References`; `IMPORTANT REFERENCE RULE` / приоритет identity; `SCENE` / style goal / environment; `TIMELINE` или `STORY FLOW`; `CAMERA / CONTINUITY`; `PERFORMANCE / ACTING`; диалог / вокал / lip-sync, если применимо; свет, материалы, production design; native audio; подробный scene-specific negative prompt; глобальный `FRAME FILL / NO BARS`. Короткий generic-промт готовым не считается.

Глобальные правила continuity: единые внешность, одежда, свет, цветокоррекция, окружение; связное 3D-пространство; физически устойчивая кинематографическая камера, контролируемая инерция, без случайной дрожи; объекты раскрываются движением камеры, а не возникают из ничего; утверждённый точный model sheet сильнее случайного визуального сходства.

**Самодостаточность / appearance lock.** Каждый production-промт, предназначенный для отдельного копирования в генератор, содержит собственный короткий `CHARACTER APPEARANCE / IDENTITY LOCK` с реальными отличительными признаками каждого важного персонажа (источник — утверждённый model sheet / `character-references.json` + свежий master). Общая «библия» сцены — только документация; промт не ссылается на неё вместо собственного блока. Владельца о внешности не переспрашивают, если identity однозначно известна.

**Качество без раздувания.** Максимум полезной конкретики при минимуме лишних слов; отдельный промт содержит свой appearance lock, владение референсами и приоритет, выполнимый тайминг действий и диалога, continuity handoff при необходимости. Качество оценивать по смыслу: отсутствие буквального заголовка в старом промте — не дефект, если защита очевидна. Правила слотов Topview — `SYNC-RUNBOOK.md`.

**Engine routing — русский диалог.** Любая сцена со слышимым разговорным диалогом на русском использует **Wan 3**: Seedance 2.5 в текущем workflow недостаточно надёжен для естественной русской речи, произношения и lip sync, и автоматически такой сцене не назначается — исключение только по новой явной команде владельца для конкретной сцены. При чтении существующей сцены с `dialogue.language = ru` проверять `target_engine = Wan 3`; при существенной переработке исправлять старое назначение в рамках того же Scene ID. Правило не требует перезапускать активную slow-задачу или менять утверждённый результат без решения владельца.

## 6. Instruction / handoff maintenance и Documentation Duty

Есть **семь** обязательных документов; их канон — `main`. Любое материальное нововведение документируется **в том же рабочем цикле**. Материальным считается: новая функция сайта; новый backend / сервис; смена источника истины; смена workflow / sync; новое обязательное правило промтов; новый тип статуса; новая процедура восстановления; смена порядка takeover; новая постоянная интеграция.

Definition of Done: (1) обновить релевантные инструкции; (2) тот же `NEW-CHAT-HANDOFF.md`, если важно следующему чату; (3) `PROMPT-STYLE-GUIDE.md`, если менялся стандарт промтов; (4) `python3 scripts/cert_github.py .`, тесты, push; (5) `project-status.json` / Pages, если затронуты; (6) Notion-указатель, если меняется способ работы; (7) резервные копии — best-effort, `pending/stale` не блокирует; (8) не создавать параллельных «новых финальных» инструкций. Временные runtime-факты (очередь, ETA, текущий SHA) по инструкциям не размножаются — их читают из живых JSON.

**Непрерывная передача знаний.** Любое подтверждённое знание, улучшение, ограничение модели, удачная практика, выбор engine, особенность prompt-writing, reference handling, continuity, генерации, монтажа, сайта, sync / восстановления или способ предотвратить найденную ошибку нельзя оставлять только в чате. Определить, к какой инструкции оно относится, и записать в том же цикле; если важно для продолжения — ещё и в handoff; если меняет стандарт промтов — в `PROMPT-STYLE-GUIDE.md`. Не размножать чисто эфемерные факты (очередь, ETA, текущий SHA). Принцип: если подтверждённая новая информация улучшает будущую работу, она должна пережить текущий чат через каноническую документацию.

## 10. Slow / Topview

Каноническая принадлежность slow — свежий master и `project-status.json.slow_scenes`. Пассивная телеметрия master не меняет. Исключение — цикл активного монитора: он может добавить **существующий Scene ID** в canonical slow при доказанной новой задаче существующей сцены и обновить привязку (Scene ID для совсем нового промта монитор не создаёт — только с согласия владельца).

Для каждой сцены: использовать её точную проверенную задачу; `queueCount` и ETA провайдера брать только из этой задачи; историческое ETA хранить отдельно; очередь и ETA между сценами не копировать; нет доказанной привязки — `verified=false` и очередь / ETA как факт не показывать.

`success` → технически завершено. Topview-managed slow снимается автоматически, когда терминальной становится **последняя** активная задача сцены (пока есть другие активные — slow остаётся). Редакторский статус не меняется: success ≠ approval; приёмка — только решение владельца. Модель состояния, слоты (ёмкость 6), публикация и publish gate — `SYNC-RUNBOOK.md` («Canonical Topview state» и далее).

## 14. Поведение нового сменщика

Новый чат должен:
- сначала прочитать все семь документов;
- подтвердить доступ к чтению и записи репозитория и возможность проверок (валидатор, тесты, Pages) перед редактированием;
- проверить живые статусы и роль писателя (`monitor_role.py`, `monitor-role.json`);
- не переспрашивать известные IDs, роли хранилищ, Scene ID и правила стиля промтов;
- не предлагать владельцу «вставить самому», если инструменты позволяют выполнить каноническую запись;
- доводить изменения до конца: коммит → sync → валидатор → статус → Pages → документация и резервные копии, где применимо;
- чётко отделять факт, рекомендацию и то, что требует решения пользователя;
- спрашивать владельца только о творческих и редакторских решениях, неоднозначной привязке «задача ↔ сцена», approval, rerender, удалении и закрытии сцен и о том, что канон не позволяет решить безопасно; детерминированное обслуживание (проверки, восстановление, формат, статусы) делается инструментами.

Если нет возможности записи в репозиторий, агент остаётся review-only и прямо сообщает ограничение, но не создаёт новый master.

## 15. Персонажи / референсы — обязательный takeover слой

До «готов продолжать» новый чат открывает на Control Center вкладку «Персонажи / Референсы» (`references.html`) и читает `character-references.json`, строит рабочую карту **каноническое имя → алиасы → точный model sheet → текущее использование в сценах → отличительные признаки / костюм** и сверяет её со свежим master. Реестр содержит утверждённые model sheets: Серёга (Канцлер / The Chancellor), Юля, Паша (JEDI-A / Navy Jedi), Артём (Bearded Jedi), Илюша (Hooded Jedi), Саша (JEDI-B / Glasses Jedi), Лёша (PURPLE), Виталик (BLACK), а также Маша Лагуна, Лучик, Рыжик, Алеся — актуальный состав и сцены всегда в `character-references.json`. «Серёжа» трактуется как «Серёга», если контекст однозначен; алиасы автоматически на других людей не расширяются.

На запросы вида «Паша говорит Саше», «заходит Серёжа» редактор не просит описывать внешность заново, а разрешает имена через реестр и текущий master: сохраняет identity, использует утверждённый model sheet как PRIMARY identity reference (если доступен) и даёт достаточное текстовое описание внешности, одежды и роли. Персонаж не из реестра, но однозначно заданный референсами текущей сцены (например, Маша-Лагуна или конкретный офицер), берётся из маппинга сцены. Только при реальной неоднозначности, которую канон не снимает, задаётся уточняющий вопрос.

`character-references.json` — реестр и публикационный слой, не второй master; поле `scenes` — текущее использование в активных сценах. При конфликте с устаревшим полем сначала сверять свежий master; точный утверждённый model sheet всегда сильнее случайного сходства группового кадра.

## 18. Topview Scene Intake — привязка к существующей сцене и новая сцена

Классификация, привязка к существующей сцене и запрет автоматического нового Scene ID — `SYNC-RUNBOOK.md` раздел 18. Для **новой сцены по согласию владельца** действует импорт:
- у задачи должны быть конкретный task ID, модель и доступный фактический промт;
- перед записью — `git pull` и свежий master; новый ID = следующий неиспользованный стабильный Scene ID, закрытые не переиспользуются;
- промт, фактически отправленный в Topview, сохраняется **дословно** как исторический исходный промт — его нельзя задним числом «улучшать» и выдавать улучшенную версию за использованную;
- рядом создаются русский заголовок, «Контекст использования», «Референсы» (если известны) и «Что происходит»; имена персонажей разрешаются через `character-references.json` и текущий master;
- активная задача → сцена в canonical slow; `success` → `RESULT_RECEIVED`, но не `APPROVED`; failed / cancelled — без авто-rerun;
- после записи — обычный sync, валидатор, `project-status.json`, Pages, обновление привязки и телеметрии.

Автоматика не может auto-approve, удалять, снимать slow без доказанной привязки, переписывать существующий промт по смысловому сходству и автоматически rerun.
