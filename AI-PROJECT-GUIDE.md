## 3. Master: как вести `video-prompts.md`

- Единственный master — `video-prompts.md` в `main`. Не создавать `v2`, `final`, `copy`, `final-final`. `project-status.json` генерируется и вторым master не является.
- Перед каждой записью — `git pull` и чтение свежего master.
- Менять только нужную сцену и связанные оглавление / счётчики / статус / slow-метки. Минимальный diff. Процедура записи — `SYNC-RUNBOOK.md` §3–5.
- Scene ID стабильны и не перенумеровываются; закрытые ID не переиспользуются никогда. Актуальный список зарезервированных ID — `project-status.json.reserved_scene_ids` и строка «Сцены … удалены из active master» в свежем master; в инструкциях список не дублируется. Закрытые «🎞 В фильме» сцены в master не возвращать.
- Если следующий Scene ID однозначно следует из свежего master (`project-status.json.latest_scene` и зарезервированные ID), не спрашивать владельца — брать следующий новый стабильный ID. Новую сцену из Topview-задачи заводят только с согласия владельца.
- Готовая сцена убирается из активного master только по решению владельца, что результат принят и промт не нужен (кнопки «🎞 В фильме» / «Не нужна»); `Topview success` для этого недостаточно.
- `NEEDS_FIX` и `NEEDS_RERENDER` не разрешают автоматическую переписку или перезапуск; разбор — по одной сцене.
- Slow-сцены не перезапускать без решения владельца. Canonical slow снимает **только явная применённая кнопка владельца**; одна метка slow в карточке — `SYNC-RUNBOOK.md` (верхние блоки).
- Master — UTF-8 без BOM, только LF, не более одной пустой строки подряд (проверяет валидатор).

## 14. Поведение нового сменщика

Новый чат должен:
- сначала пройти короткий приём D7 либо обязательное полное чтение семи документов по условиям раздела «Формат takeover и решение D7»;
- подтвердить доступ к чтению и записи репозитория и возможность проверок (валидатор, тесты, Pages) перед редактированием;
- проверить живые статусы и роль писателя (`monitor_role.py`, `monitor-role.json`);
- не переспрашивать известные IDs, роли хранилищ, Scene ID и правила стиля промтов; не импровизировать другую архитектуру; продолжать с текущего состояния;
- не предлагать владельцу «вставить самому», если инструменты позволяют выполнить каноническую запись;
- доводить изменения до конца: коммит → sync → валидатор → статус → Pages → документация и резервные копии, где применимо;
- чётко отделять факт, рекомендацию и то, что требует решения пользователя; не приписывать владельцу решений, которых он прямо не выражал;
- спрашивать владельца только о творческих и редакторских решениях, неоднозначной привязке «задача ↔ сцена», approval, rerender, удалении и закрытии сцен, небезопасных действиях, сбое, который не исправился после одной проверенной попытки, и о том, что канон не позволяет решить безопасно; детерминированное обслуживание (проверки, восстановление, формат, статусы) делается инструментами;
- при ограничении инструмента честно назвать конкретный недоступный шаг.

Если нет возможности записи в репозиторий, агент остаётся review-only и прямо сообщает ограничение, но не создаёт новый master. Цель takeover: владелец говорит только новую творческую или рабочую задачу, а сменщик уже знает инфраструктуру и процесс.

## 15. Персонажи / референсы — обязательный takeover слой

До «готов продолжать» новый чат открывает на Control Center вкладку «Персонажи / Референсы» (`references.html`) и читает `character-references.json` (без base64 в рабочий текст), строит рабочую карту **каноническое имя → алиасы → точный model sheet → текущее использование в сценах → отличительные признаки / костюм** и сверяет её со свежим master. Реестр содержит утверждённые model sheets: Серёга (Канцлер / The Chancellor), Юля, Паша (JEDI-A / Navy Jedi), Артём (Bearded Jedi), Илюша (Hooded Jedi), Саша (JEDI-B / Glasses Jedi), Лёша (PURPLE), Виталик (BLACK), а также Маша Лагуна, Лучик, Рыжик, Алеся — актуальный состав и сцены всегда в `character-references.json`. «Серёжа» трактуется как «Серёга», если контекст однозначен; алиасы автоматически на других людей не расширяются.

На запросы вида «Паша говорит Саше», «заходит Серёжа» редактор не просит описывать внешность заново, а разрешает имена через реестр и текущий master: сохраняет identity, использует утверждённый model sheet как PRIMARY identity reference (если доступен) и даёт достаточное текстовое описание внешности, одежды и роли. Персонаж не из реестра, но однозначно заданный референсами текущей сцены (например, Маша-Лагуна или конкретный офицер), берётся из маппинга сцены. Только при реальной неоднозначности, которую канон не снимает, задаётся уточняющий вопрос.

**Коты.** Лучик — бело-серый пушистый длинношёрстный кот, постоянный синий световой меч (в Scene 13 — тот же Лучик без меча, говорящий кот на коленях PURPLE; синий меч, вертикальная поза и храм из его model sheet в сцену Совета не попадают). Рыжик — рыжий пушистый длинношёрстный табби-кот, постоянный зелёный световой меч. Коты — обычного домашнего масштаба. Для котов всегда индивидуальный точный model sheet как identity authority плюс короткий текстовый lock; парный или композиционный референс не переопределяет морду, окрас, шерсть и пропорции.

`character-references.json` — реестр и публикационный слой, не второй master; поле `scenes` — текущее использование в активных сценах. При конфликте с устаревшим полем сначала сверять свежий master; точный утверждённый model sheet всегда сильнее случайного сходства группового кадра. Утверждённый model sheet — авторитет по внешности; текущий master — авторитет по использованию в сценах.
