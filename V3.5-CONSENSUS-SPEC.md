**Status:** REVIEWED SPEC REV.2 — READY FOR PHASE 0 / IMPLEMENTATION STILL GATED  
**Date:** 17.09.2026  
**Review checkpoint:** post-review by Grok, DeepSeek and Gemini; Claude full review was already incorporated before its session limit.  
**Purpose:** Consolidate independent reviews from GPT-5.6 Sol, Claude, Gemini, DeepSeek, and Grok into one verified implementation specification for the next project revision.  
**Scope:** Website/UI, synchronization architecture, instructions, machine status, prompt schema, and targeted prompt audit.  
**Out of scope for this document:** changing the canonical `video-prompts.md`, rewriting prompts, changing scene IDs, restarting renders, modifying the current site, or changing the source-of-truth architecture.

## 0. Executive decision

The current v2 architecture is stable enough to remain the baseline. V3.5 should be an **additive production-intelligence layer**, not a rebuild.

The target is:

- keep Google Drive `video-prompts.md` as the only editable canonical master;
- keep GitHub as a read-only public mirror and GitHub Pages source;
- keep stable sparse scene IDs;
- preserve the existing validator and slow-generation safeguards;
- preserve the lightweight client-side viewer;
- add better production-state visibility, search/filtering, dependencies, freshness checks, and model metadata;
- reduce instruction drift without reducing recovery safety;
- audit prompts selectively instead of rewriting all prompts;
- test disputed prompt-engineering ideas by A/B generation instead of adopting them by vote.

This specification records decisions only. **Nothing in this file authorizes an automatic edit of the current master, site, prompts, instructions, Library, Notion, or workflow.**

# 3. Decision legend

Every proposal in this specification is assigned one of five states:

- **ACCEPT** — suitable for V3.5 as proposed or with trivial implementation detail.
- **MODIFY** — underlying idea is useful, but the proposed implementation must change.
- **TEST** — do not make a project-wide rule until an A/B or capability test supports it.
- **REJECT** — conflicts with verified architecture, creates unacceptable risk, or lacks sufficient basis.
- **ALREADY EXISTS** — current project already implements the useful part.

Consensus is evidence, not authority. A 4-to-1 vote does not override a verified architectural invariant or an actual generation result.

## 5.2 Project state model

V3.5 should separate **production state** from **render state**.

### Production state
Proposed controlled vocabulary:

- `DRAFT`
- `READY`
- `NEEDS_FIX`
- `RESULT_RECEIVED`
- `NEEDS_RERENDER`
- `APPROVED`
- `IN_EDIT`
- `CLOSED`

### Render state
Separate controlled vocabulary:

- `IDLE`
- `SLOW_PENDING`
- `FAILED`
- `COMPLETED`

**Reason:** a scene can be production-ready while simultaneously being in slow generation. Replacing `⏳ В МЕДЛЕННОЙ ГЕНЕРАЦИИ` with one generic status would weaken a critical duplicate-render safeguard.

### Definition of Done

DeepSeek's underlying proposal is accepted with refinement.

A scene becomes `CLOSED` only when:

1. the generated result is reviewed;
2. the user approves the intended take;
3. the take is placed in the current edit, or the user explicitly decides placement is not required;
4. continuity/regeneration needs are resolved;
5. no further prompt iteration is planned.

Only then may the prompt be removed from the active master under the existing removal rule.

**Decision:** **ACCEPT / MODIFY**

- GitHub workflow: `.github/workflows/sync-from-drive.yml`;
- generator/validator: `scripts/build_project_status.py`;

V3.5 should extend this existing generator instead of introducing a second status producer. New fields such as `canonical_master_sha256`, `scene_meta`, `dependencies`, and `instruction_sync` must be generated or validated by this pipeline. No user or AI should manually edit them in `project-status.json`.

The canonical hash should be calculated deterministically from the exact canonical master bytes used for validation/sync. Its purpose is freshness comparison, not version numbering.

### Dependency extraction

**MODIFY** Claude's proposal to infer every dependency by regex from prose.

Preferred order:

1. explicit structured metadata if present;
2. validator-assisted extraction from a controlled metadata line;
3. prose inference only as a warning/suggestion, never as authoritative data.

Do not make production-critical dependency state depend solely on natural-language parsing.

# 10. Prompt schema V3.5

## Goal

Normalize discoverability and model metadata **without forcing every scene into identical prose**.

### Required metadata layer

Each active scene should eventually expose:

```text
Scene ID
Title
Target engine/model
Duration
Production state
Render state
References and their roles
Dependencies / alternatives
Dialogue: yes/no
Dialogue language
```

### Prompt body

Use sections as needed:

```text
[REFERENCE ROLES]
[REFERENCE PRIORITY]
[SCENE / INTENT]
[TIMELINE or ACTION]
[CAMERA]
[IDENTITY / COSTUME LOCKS]
[SPATIAL CONTINUITY]
[PERFORMANCE]
[LIGHTING / STYLE]
[AUDIO / DIALOGUE]
[NEGATIVE PROMPT]
```

Not every simple scene requires every section.

### Important principle

**Schema consistency is for finding and validating information. Prompt wording remains scene-specific.**

# 11. Prompt-engineering proposals: decisions

## Long negative prompts

DeepSeek suggested a hard limit of 8–12 items.

**Decision: TEST / MODIFY**

Rule for V3.5:
- remove redundant negatives;
- preserve scene-specific failure-mode constraints;
- do not enforce an arbitrary global item count.

Example: scene 13 legitimately needs cat-specific negative constraints that would be lost under a mechanical limit.

---

## Russian phonetic transliteration

DeepSeek recommended Latin phonetic duplicates for Russian dialogue.

**Decision: TEST**

Do not add globally.

A/B test:
- A: exact Russian text only;
- B: exact Russian text + carefully designed phonetic line.

Evaluate:
- pronunciation;
- lip sync;
- whether the model speaks duplicated content;
- naturalness.

If an engine consistently benefits, implement only in that engine's adapter.

---

## Repeating identity/costume markers mid-prompt

Gemini suggested reasserting key visual identity markers later in 30-second prompts.

**Decision: TEST / targeted use**

Potentially useful for long/high-drift scenes, but not a mandatory pattern.

---

## Fixed/static lighting instruction

Gemini suggested fully static lighting/color temperature.

**Decision: MODIFY**

Preferred wording:
- preserve established lighting sources, color balance, exposure continuity, and motivated physical changes;
- do not freeze physically correct light changes caused by camera/subject movement.

---

## Spatial continuity rule

DeepSeek and GPT support it.

**Decision: ACCEPT as a design principle, not boilerplate mandate**

Use explicitly where:
- camera traverses complex space;
- action depends on existing geometry;
- characters land/interact with structures;
- a one-take spatial reveal is important.

Do not paste it mechanically into static dialogue scenes if it adds no value.

---

## Fixed 5–8 shots per 30 seconds

Suggested as a Seedance recommendation.

**Decision: REJECT as a global rule**

Shot/beat count follows scene needs:
- one continuous take can be correct;
- dialogue may need 2–4 beats;
- complex action may need several phases.

---

## 720p as universally better Seedance prompt adherence

Suggested by DeepSeek.

**Decision: REJECT unless independently verified for the specific provider/model mode.**

Do not make provider-specific assumptions a canonical project rule.

---

## `4K 24fps` in prompts labeled Wan 3

Current prompt/model adapter parameters require a separate verified compatibility review before next use.

**Decision: FIX AT MODEL-ADAPTER LAYER, not mass rewrite now.**

Do not silently alter active prompts while building this specification.

# 13. A/B experiments before prompt-wide rules

No experimental result becomes a canonical rule without a real output comparison. Experiments are **opportunistic**, not a mandatory research backlog: run them only when a scene genuinely needs a new generation.

### Experiment priority

- **P1 / potentially blocking a needed future render:** Russian native-audio / lip-sync behavior for a dialogue scene when the next required render depends on it.
- **P2 / useful when a complex scene fails:** Director vs Reliability version for overloaded action.
- **P3 / non-blocking optimization:** negative-prompt density.
- **P3 / non-blocking optimization:** mid-scene identity/costume reminder.

Do not delay film completion just to complete P3 experiments.


## Experiment A — Russian dialogue
A: Russian text only  
B: Russian + phonetic helper

Measure:
- pronunciation;
- synchronization;
- duplicate speech;
- acting naturalness.

## Experiment B — negative prompt density
A: current scene-specific negative block  
B: deduplicated short negative block

Measure:
- target failure frequency;
- prompt adherence;
- identity stability.

## Experiment C — high-complexity action
A: Director version  
B: Reliability version with fewer independent events

Measure:
- identity;
- spatial continuity;
- event completion;
- usable seconds.

## Experiment D — identity reminder
A: identity defined only in references/locks  
B: one targeted mid-scene identity/costume reminder

Measure:
- late-clip drift;
- costume/color preservation.

Experiments should be run only when a scene actually needs another generation. Do not waste current accepted or slow jobs purely to test the system.

### Recovery
- Handoff remains usable.
- Takeover instructions do not assume unavailable write capabilities.
- Recovery does not promote Library or GitHub into a competing master.

- **User** owns creative acceptance, privacy decisions, and final production-state decisions.

- **A/B output** is the arbiter for disputed prompt-engineering claims when a real generation is needed.

# 21. Bottom line

V3.5 should not be “a prettier version of V2”.

It should make the existing system more aware of:
- **what is current;**
- **what is rendering;**
- **what is ready;**
- **what depends on what;**
- **which model a prompt targets;**
- **whether the instructions an external AI is reading are fresh;**
- **which prompt-engineering ideas are verified versus merely suggested.**

The strongest parts of V2 — one Drive master, sparse stable IDs, validation, slow-render protection, lightweight Pages viewer, and recovery documentation — remain the foundation.
